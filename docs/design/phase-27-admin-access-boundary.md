## Problem Statement

The server's optional shared API key leaves admin routes anonymous when no key is
configured. Loopback-only validation protects the direct listener but cannot prove
that a reverse proxy or tunnel has not exposed it. Phase 27 must make non-local
admin deployments fail closed while keeping the default local workflow frictionless.

## What Makes This Valuable

The useful outcome is deliberately boring: an unsafe deployment refuses to start,
and an unauthenticated caller never reaches admin state. The operator gets a clear
unlock flow instead of a mysterious broken console, while local development still
starts with one command.

## Constraints

- Local-first development remains anonymous only on `local + loopback`.
- Staging, production, unknown non-local environments, and non-loopback listeners
  require an effective admin key.
- Existing `server.api_key` installations need a one-phase compatibility fallback.
- No accounts, RBAC, cookies, durable sessions, or tenant-selection changes.
- Browser credentials remain in page memory and never enter URLs or storage.
- The exact `/admin` path is a data-free unlock shell; every existing and future
  `/admin/*` route inherits one centralized policy.

## Premises

1. The verified Phase 26 high-severity finding is the highest-value next problem
   after the Phase 23-26 knowledge repair roadmap closed.
2. A distinct admin boundary is necessary even when the listener binds to loopback.
3. One operator bearer credential is sufficient for this local-first stage.
4. Local usability is worth preserving when both environment and network binding
   explicitly indicate loopback-only development.
5. Full identity and authorization should wait for concrete multi-user demand.

## Approaches Considered

### Approach A: Environment-Aware Admin Fail-Closed

Add a dedicated admin key with legacy fallback, strict non-local validation,
centralized `/admin` classification, and an in-memory browser unlock shell.

- Effort: Medium
- Risk: Medium
- Reuses: existing config validation, Bearer/X-API-Key parsing, middleware order,
  static admin UI, and secret-redaction patterns.
- Advantage: closes the deployment risk without breaking default local startup.
- Cost: policy has an explicit local exception and requires careful browser boot.

### Approach B: Universal Admin Key

Require a key for every admin request in every environment.

- Effort: Small to Medium
- Risk: Low security risk, medium adoption risk
- Reuses: the same existing auth machinery.
- Advantage: simplest rule and smallest policy state space.
- Cost: every local run requires secret setup and browser unlock.

### Approach C: Accounts, Sessions, And RBAC

Build a durable identity system with login, roles, sessions, and per-action policy.

- Effort: Extra Large
- Risk: High
- Reuses: little beyond current route middleware.
- Advantage: supports future shared administration and attribution.
- Cost: creates substantially more security-sensitive surface than the current
  product requires.

## Recommended Approach

Approach A. It directly remediates the observed access-control failure, protects
reverse-proxied deployments, preserves the local-first experience, and leaves a
clean future migration path to real identity without pretending an API key is RBAC.

## Open Questions For Stage 2

1. What is the smallest bootstrap endpoint or static-shell split that keeps
   `/admin` locked without duplicating the existing application?
2. Which shared frontend request helper can guarantee every admin fetch receives
   the in-memory credential and handles `401` consistently?
3. Should the capability response be served from a non-admin endpoint or encoded
   in the minimal shell response while exposing only `admin_auth_required`?
4. Which constant-time comparison helper best fits the current key-set structure?

These are architecture questions for autoplan, not unresolved product choices.

## Success Criteria

- Unsafe non-local admin configurations fail before listening.
- All admin data and mutation routes are protected by one prefix-safe policy;
  the exact `/admin` shell exposes no admin state.
- Existing secured deployments migrate without immediate breakage.
- Local loopback development remains one-command and anonymous by default.
- The browser can unlock an authenticated admin console without persisting or
  leaking the credential.
- Existing chat, experience, tenant, and admin payload behavior remains stable.

## What I Noticed About The Decision

- The selected `A` keeps security proportional to the current product stage.
- The decision treats the Phase 26 finding as a release boundary, not as permission
  to grow Phase 27 into a general identity platform.
- Preserving local-loopback use is an explicit product constraint, not an accidental
  authentication bypass.
